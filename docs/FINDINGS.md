## 2. What was established without a GPU

These are facts found while building the harness. Each one changes what a "fair" comparison means.

1. **The newest Triton image with TRT-LLM is 26.07.** The Triton 26.08 and 26.09 release notes say the TRT-LLM container was not published. The pair compared is therefore Triton 26.07 / TRT-LLM 1.2.1 (the latest *stable* TRT-LLM; 1.3 is still at rc29) against vLLM v0.30.0 (two weeks old on the date of writing).
2. **The Triton LLM-API model can't force output length out of the box.** Its `helpers.py` forwards only a whitelist of `SamplingParams`, and `ignore_eos` isn't on it. Without that, the two engines stop at different EOS points, and tokens/s and latency compare different amounts of work. Fix: a 3-line, auditable patch ([UPSTREAM.md](../deploy/helm/llm-serving/files/triton/UPSTREAM.md)). The load generator refuses to run if the deployed model doesn't declare the input.
3. **vLLM silently applies the model's sampling defaults; TRT-LLM doesn't.**
   - Qwen's `generation_config.json` sets `repetition_penalty: 1.1, temperature: 0.7, top_k: 20, top_p: 0.8`. By default vLLM uses these for any field the request omits.
   - TRT-LLM 1.2.1 reads that file only for stop-token IDs (checked in `sampling_params.py`).
   - The vLLM deployment therefore sets `--generation-config vllm`, and the client sends every sampling field explicitly.
4. **Triton streams cumulative text.** TRT-LLM's `CompletionOutput.text` is the full text so far, and the Triton model streams that field.
   - A naive client double-counts text, and also misreads TTFT if it waits for a "delta".
   - Payload grows quadratically. At about 4 characters per token (an assumption, not a measurement), a 256-token answer carries about 130 KB of streamed text versus about 1 KB of deltas.
   - The client detects the mode from the first two chunks.
5. **Memory knobs aren't equivalent.** vLLM's `--gpu-memory-utilization` caps *total* usage. TRT-LLM's `free_gpu_memory_fraction` applies to memory *left after* loading weights. Both are instead pinned to the same **8 GiB KV-cache byte budget** (`--kv-cache-memory-bytes` / `max_gpu_total_bytes`).
6. **KV cache isn't the bottleneck at this scale.**
   - Qwen2.5-1.5B uses 28 KiB of KV per token (28 layers × 2 KV heads × 128 dim × K/V × 2 bytes), so 8 GiB holds about 300k tokens.
   - The worst case here (64 × 558 tokens) needs about 36k tokens.
   - The benchmark therefore measures compute and scheduling efficiency, not behavior under KV pressure or preemption.
7. **`kubectl port-forward` is a measurement hazard.** It tunnels through the API server. The default client therefore runs *in-cluster* against the ClusterIP service. GPU sampling stays on the operator's machine and is matched to concurrency levels by wall-clock time.

## 3. Comparability: what is identical and what is not

| Aspect | vLLM | Triton + TRT-LLM | Identical? |
|---|---|---|---|
| Weights | HF snapshot @ pinned SHA from shared PVC, offline | same | ✅ |
| Input text / tokens | pre-templated string, no BOS | same | ✅ |
| Output length | 256, `ignore_eos` | 256, `sampling_param_ignore_eos` (patched) | ✅ (verified per request in report) |
| Decoding | greedy via `temperature=0` | greedy via `top_k=1` | ⚠️ same intent, different parameter. Kernel-level numerics differ, so greedy texts may diverge. The report measures agreement |
| Precision | BF16 (`dtype=auto`) | BF16 (`dtype: auto`) | ✅ |
| Max seqs / max len / batched tokens | 64 / 4096 / 8192 | 64 / 4096 / 8192 | ✅ (asserted by tests) |
| KV-cache size | 8 GiB | 8 GiB | ✅ |
| Prefix caching | off | off (`enable_block_reuse: false`) | ✅ |
| Chunked prefill | always on (V1) | `enable_chunked_prefill: true` | ✅ (configured) |
| CUDA graphs | on, vLLM's default capture sizes | on, padded up to 64 | ⚠️ different capture policies |
| Other scheduler defaults | vLLM defaults | TRT-LLM defaults (e.g. overlap scheduler) | ❌ left at each engine's default, deliberately |
| Non-KV memory (activations, graphs, workspace) | engine-managed | engine-managed | ❌ so GPU-memory peaks reflect config, not load |
| Serving path | Python API server → engine | C++ HTTP frontend → Python backend stub (IPC) → LLM API → engine | ❌ part of what is being compared |
| Stream encoding | deltas, OpenAI JSON | cumulative text, Triton JSON | ❌ part of what is being compared |
| Token count source | server `usage` | inferred from `finish_reason == length` | ⚠️ equal by construction when lengths are forced; mismatches are flagged |
| TTFT | first non-empty chunk, client clock | same | ✅ (incl. detokenization delay on both) |

Takeaway: this compares **two serving stacks as deployed**, not two attention kernels. Differences in the HTTP/Python layers and stream encoding are deliberately included, since a user of either stack pays for them.

## 4. Hypotheses to check once data exists (unverified)

These are reasons a difference *might* appear. None is a result.

- **TTFT at low concurrency.** The Triton path adds a C++→Python-backend hop and runs request handling inside one Python model instance. Compare TTFT p50 at c=1, and check whether the gap shrinks relative to total E2E.
- **Streaming overhead at high concurrency.** The cumulative-text payload (§2.4) grows with output length and stream count. If Triton's E2E degrades faster than its TPOT, look here. CPU-limit throttling of the pod (`cpu: 8`) is also worth checking.
- **Decode throughput.** Both use CUDA graphs and in-flight batching. Differences at c=16–64 would more likely come from scheduler policy than from kernels for a 1.5B model. Both engines can overlap CPU scheduling with GPU work: TRT-LLM's overlap scheduler is on unless `disable_overlap_scheduler` is set, and vLLM v0.30.0's `async_scheduling` defaults to `None`, letting the engine decide. Check each server's startup log to see what was actually active.
- **GPU memory.** Expect similar peaks, since both preallocate an 8 GiB KV cache. Differences come from CUDA-graph pools and workspace, not from load.

## 5. Limitations

- One GPU type, one small model, one run per backend. No confidence intervals. Re-run at least 3× (fresh pod each time) before drawing conclusions from differences under ~10%.
- Closed-loop load only (fixed concurrency). No open-loop/Poisson arrivals, so no queueing-delay or SLO-goodput analysis.
- Short prompts (≤ 302 tokens) and a KV budget far above need. Long-context and memory-pressure behavior aren't tested.
- Greedy decoding only. Sampling-path performance isn't covered.
- Client-side timings include in-cluster networking and SSE parsing on both sides. Server-side timings aren't used for the headline metrics.
- The Triton side runs a *patched* NVIDIA model file (whitelisting two existing `SamplingParams` fields).
- Clock skew between the operator's machine and the cluster can misattribute GPU samples near level boundaries. It was about 0.15 s in local testing, against 1 s sampling.
